# AvdbAsst

把上游资源站的检索包成一个可以直接被浏览器「自定义搜索引擎」调用的网页。

配好之后，在任意页面选中一段文字 → 右键 → 用本站搜索，就能直接落到结果页。
典型用法：看到番号，选中，右键搜。

> 页面上显示的名称是**「资源搜索」**，界面中不含上游产品名。

```
https://你的地址/s?q=BOBB-456
```

- 纯 Go 标准库实现，**零第三方依赖**
- 单文件二进制，前端资源全部内嵌
- 结果以**列表**呈现，只加载文字信息、不拉取海报图，首屏更快
- 搜索、下载器提交、上游地址与令牌 **全部可在网页里配置**
- 搜索**没有条数上限**，能搜到多少就展示多少；超出每页条数的部分自动分页
- 每页条数可选 10/50/100/200/300/500/1000 或「全部」，设置一次**永久记住**
- 标签页标题是否带上搜索关键词可在设置页开关，**默认不带**（只显示「资源搜索」）
- 结果页可按站点/板块/分类/属性**筛选**、按体积或时间**排序**，
  还能按标题关键词**过滤与反向过滤**（`-词` 即排除）；
  **筛选条件写在 URL 里，翻页、跳页全程带着走**
- 结果支持**多选、全选、批量提交下载、批量复制磁链**
- 下载器标识可就地**探测**：只用访问令牌就能问出上游到底配了哪个下载器，不必猜
- 配置写入挂载目录，**容器重建不丢**
- 右上角常显**版本号**（如 `v1.1.0`）；构建标识（`分支@短sha`）只出现在设置页与 `/healthz`
- 推送到 GitHub 自动构建 amd64 / arm64 双架构镜像并推送到 Docker Hub

## 快速开始

### 方式一：Docker Compose（推荐）

```bash
git clone https://github.com/LIUBANGJIAN/AvdbAsst.git
cd AvdbAsst
mkdir -p data
docker compose up -d
```

然后打开 `http://<你的机器IP>:8080/settings`，填入上游地址和 API Key，保存即可。

### 方式二：docker run

```bash
docker run -d \
  --name avdbasst \
  --restart unless-stopped \
  -p 8080:8080 \
  -v "$(pwd)/data:/data" \
  -e TZ=Asia/Shanghai \
  liubangjian/avdbasst:latest
```

### 方式三：直接跑二进制

```bash
go build -o avdbasst .
AVDB_CONFIG_DIR=./data ./avdbasst
# 浏览器打开 http://localhost:8080/settings
```

## 目录持久化

配置（含上游地址、API Key、访问口令）保存在 **`$AVDB_CONFIG_DIR/config.json`**：

| 环境 | 配置目录 |
| --- | --- |
| 容器内 | `/data`（Dockerfile 已设好） |
| 本地运行 | `.`（当前目录），可用 `AVDB_CONFIG_DIR` 改 |

**要让它真正持久，必须把宿主目录挂载到 `/data`：**

```yaml
volumes:
  - ./data:/data
```

没挂载会怎样：容器照常运行、也能在页面里改配置，但容器一重建配置就没了。
设置页面会显示配置目录路径与「可写」状态，方便自查。

写入是**原子**的：先写临时文件、`fsync`、再 `rename`。
中途断电最多丢掉最后一次修改，不会留下半截 JSON 让下次启动直接失败。
文件权限 `0600`（里面是明文令牌）。

## 页面配置

打开 `/settings` 即可配置：

| 项 | 说明 |
| --- | --- |
| 上游地址 | 上游实例地址，如 `http://192.168.1.20:8000` |
| API Key | 上游 `X-API-Key`，在上游的「控制中心 → 访问令牌」创建 |
| 下载器 | 提交离线下载用的下载器标识，**必填**。用**下拉选择**；不知道该选哪个就点「检测」，见下节 |
| 保存路径 | 提交离线下载的目录，**必填且不能为空**（上游会直接拒绝空目录） |
| 每页条数 | 结果页每页显示多少条，设置页与结果页两处都能改，**保存后永久生效** |
| 网站名称 | 决定浏览器标签页标题里带不带当前搜索关键词，**默认关闭**，见下节 |
| 访问口令 | 给本站自己加的访问控制，见下节 |

「请求超时」「结果上限」两个高级项已下线；搜索结果**默认不设任何条数上限**，
详见下面的「关于结果上限」。

点「保存设置」即时生效，**不需要重启容器**。

下载相关只有两个按钮，彼此独立，任一失败不影响其余：

| 按钮 | 打到上游的接口 | 用途 |
| --- | --- | --- |
| 测试连接 | `GET /api/v1/articles/torrents` | 保存前确认地址和令牌能不能用 |
| 检测 | 对每个候选标识各调一次 `GET /api/v1/config/downloader/directories` | 一次问清"上游配了哪个下载器、它下面有哪些目录"，并把结论列成清单 |

两个接口的鉴权都是 `API Key/JWT`，**只需访问令牌，不需要上游账号密码**。

「检测」是**一次调用回答三个问题**：哪个下载器可用、当前选的是否有效、可用目录有哪些。
之所以不再拆成三个按钮（探测可用下载器 / 读取上游默认下载器 / 校验并列出目录），
是因为那三件事对用户其实是同一个问题——"我这套下载设置到底能不能用"；
拆开之后用户的第一反应是"我该点哪个"。

仍保留、但界面上不再有按钮的两个接口（供脚本调用）：

- `POST /api/settings/default-rule`：读上游订阅默认下载目标；
- `POST /api/settings/directories`：校验单个下载器并列目录。

### 关于结果上限

**搜索没有条数上限，能搜到多少就展示多少。**

原先有一个默认 5000 的截断值，宽泛关键词下页面会打出
「结果过多，只展示前 5000 条」——这与本站"无上限、靠分页展示全部"的定位自相矛盾。

2026-09 的修复暴露了一个更深的坑：**只把默认值改成 0 是不够的**。
老版本的 `Save()` 会把整个 Config 落盘，而 `max_results` 字段没有 `omitempty`，
所以任何一个存量 `config.json` 里都静静地躺着一个 `"max_results": 5000`；
升级二进制之后它照样被读回来，截断照旧。实测：关键词 `HD` 上游真实返回 **5954** 条，
页面却只肯收 5000 条，954 条被无声丢掉。

因此该字段被划归**部署参数**（与监听地址同级）：**只认环境变量，配置文件里写了也不再生效**，
也不再被写入文件。存量的 `max_results` 会在启动时给一条提示后自动失效，
下次在设置页保存一次配置，这个键就从文件里彻底消失。

`AVDB_MAX_RESULTS` 仍然保留，但语义是"**可选**安全阀"：**默认 `0` = 不限制**，
只有显式设置成正整数时才生效（上界 50000）。页面上不暴露该项。

### 网站名称：标签页标题带不带搜索关键词

浏览器标签页的标题有两个形状，由设置页「结果展示」里的**网站名称**开关决定：

| 开关 | 结果页标题 | 首页 / 设置页标题 |
| --- | --- | --- |
| 关闭（**默认**） | `资源搜索` | `资源搜索` / `设置 · 资源搜索` |
| 开启 | `BOBB-456 · 资源搜索` | 同上（无关键词时不出现分隔符） |

默认关闭是刻意的：标签标题会留在浏览器历史与书签里，也会被旁边的人一眼看到，
所以默认不把"正在搜什么"摆在明面上；想露的用户自己在设置页打开。

几个实现上的取舍：

- 开关**只从设置页改**，不做成 URL 参数。做成参数的话，任何一条
  `…/s?q=x&title_with_keyword=1` 的链接都能顺手改掉别人的偏好，
  而且翻页链接还会把它一路带着走。
- 关键词仍要走模板转义：它直接来自地址栏，搜 `<b>x` 时标题里是
  `&lt;b&gt;x · 资源搜索`，不会变成标签。
- 该字段在 `config.json` 里带 `omitempty`，**只在开启时落盘**。
  这是提前埋的保险：默认值不会像 `max_results` 那样被存量文件钉死，
  以后想改默认值仍然改得动；代价是"显式关闭"与"从未设置"在文件里长得一样，
  而这两者当前行为完全一致，不算损失。

### 结果页的筛选、排序与过滤

结果页顶部的工具条是一个 **GET 表单**，所有条件都在**服务端对全量结果**生效，
并写进 URL：

```
/s?q=SSIS&site=色花堂&flags=cn,hd&sort=size-desc&filter=无码%20-4K
```

| 参数 | 含义 |
| --- | --- |
| `site` / `section` / `category` | 精确匹配站点 / 板块 / 分类；空即不筛 |
| `flags` | 属性，逗号分隔，多个之间是**与**：`cn` 中文字幕、`unc` 无码、`uhd` 4K、`hd` 高清 |
| `sort` | `default` / `size-desc` / `size-asc` / `time-desc` / `time-asc`，默认不排序（保持上游顺序） |
| `filter` | 标题关键词过滤，见下 |

`filter` 的语法极简：**空格或逗号分词，词前加 `-`（或 `!`）表示排除**。

```
filter=中文字幕          → 标题必须含「中文字幕」
filter=无码 -4K          → 含「无码」且不含「4K」（后半句就是反向过滤）
filter=-SSIS             → 只要不含「SSIS」的
```

不另设"包含 / 排除"切换按钮：状态型按钮一多，用户得先看清当前处在哪个模式
才敢输入；写在输入框里则所见即所得。

**为什么筛选必须放在服务端**（这是 2026-09 修掉的一个真实缺陷）：
早先这些条件只在前端对**当前页的 DOM** 过滤，于是筛选和分页互相拆台——
筛完翻到第 2 页，条件就没了，用户得重选一遍；就算勉强留住，
第 2 页也只是"全量第 101~200 条里恰好符合条件的那几条"，条数忽多忽少、序号还会跳。
现在条件跟着 URL 走，翻页、跳页、改每页条数都会原样带上，
**筛出来的结果集是稳定的**（"共 N 条"也变成筛选后的条数）。

配套的两个细节：

- 筛选项（站点/板块/分类的下拉候选）始终基于**筛选前**的全量结果计算。
  否则选了「无码」之后，站点下拉里只剩含无码资源的站点，想换站点都点不到，
  等于把自己锁死在当前条件里。
- 属性筛选渲染成**链接**而不是按钮，加上 `noscript` 里的「应用」按钮，
  让整条工具条在**禁用 JS** 时照样可用。

**筛选栏为什么必须一行放下**（2026-09 第二次修，用户两次截图都是它）：

这条栏有 7 组控件（站点 / 板块 / 分类 / 排序 / 标题过滤 / 属性 / 每页）。
宽屏一行、窄屏折行本来天经地义，但"折行"连续两次出现在**用户自己的窗口宽度上**——
每次都在某个宽度看着挺好，换个宽度就掉下去一个「每页」。根因是两个会重复出现的机制：

- **flex 的断行依据是基准尺寸之和，不是实际渲染宽度。** 哪怕最后靠收缩挤进了一行，
  只要基准之和超了，浏览器照样提前断行。于是"看着还有空位，却掉下去一个控件"。
  一旦落在"基准超了、实际还够"的区间，就是稳定复现的两行。
- **原生 `<select>` 的宽度由最宽的 `option` 文字撑开**，与 `min-width` 关系不大：
  站点里有个「色花堂4K超清」，就把那个下拉撑到 130px，四个下拉白白多占约 100px。

现在的做法是 `flex-wrap: nowrap` + 四个下拉与「每页」**显式定宽**
（`width` 与 `min-width` 都要写——CSS 里 **min-width 优先于 width**，只写前者会被静默顶回），
**只有标题过滤框是伸缩项**，富余多少吃多少。

`nowrap` 的代价是极窄处会变成**水平溢出**，而横向滚动条比折行糟得多，
所以断点必须压在"真正放不下"的临界宽度**之下**：七件东西定宽合计约 873px，
加两级内边距与边框约 955px，再给真实浏览器的滚动条留余量，取 **980px**。
`@media (max-width: 980px)` 显式放开折行，窗口再窄就老实用折行形态——
那是"真放不下"，不是"差一点没放下"。

实测（真浏览器逐宽度量）：**981px 及以上一律一行、无溢出**；980px 及以下折行且不溢出。
布局本身没法在 `go test` 里量，所以退一步把**样式契约**钉在
`TestToolbarStaysOnOneRow`（改掉 `nowrap`、定宽或 980px 兜底，它会先红）。

### 下载器标识与保存路径：两个都是必填

上游 `GET /api/v1/articles/download/manul` 的接口契约在某一版之后变了：

| 参数 | 文档标注 | 实际行为 | 本站做法 |
| --- | --- | --- | --- |
| `tid` | 必填 | 必填 | 无条件下发 |
| `downloader` | 选填 | **必填**，缺失即 `422：查询参数 → downloader：Field required` | 无条件下发；未配置时用兜底标识 `clouddrive` |
| `save_path` | 选填 | **必填，且不接受空串**（空串回 `保存目录不能为空`） | 无条件下发；未配置时**拒绝提交**并给出可操作提示 |

也就是说，**三个参数一个都不能少，后两个都不能为空**。
"留空即省略参数"的老写法会直接撞 422——这正是本项目在它上面反复踩坑的原因
（详见文末「下载器踩坑记录」）。

本站的处理：

- 三个参数**无条件发送**，不再有"有值才带"的分支；
- `downloader` 留空时走兜底标识 `clouddrive`（CloudDrive2 桥接 115 网盘的场景）；
- `save_path` 留空时**不打上游**，直接在页面提示"去设置页填保存路径"——
  因为上游一定会拒绝，与其转发一句 422，不如就地挡住并说清原因；
- 真出错时，报错会**原样带上上游原文**，并补一句"去哪个页面改什么"。

### 怎么知道该填什么标识：点「检测」

上游没有任何"列出全部下载器"的接口（`GET /api/v1/config/{key}` 只认登录 JWT），
但**逐个候选标识各调一次目录接口，就能从它的回答反推结论**：

| 上游回答 | 含义 |
| --- | --- |
| `不支持的下载工具` | 这个类型根本不存在 |
| `未找到该下载工具配置` | 类型合法，但上游没配 |
| 其余（**含 CloudDrive 报"目录读取失败"**） | ✅ **已配置** |

最后一条是反直觉但关键的一条：CloudDrive 读目录失败（gRPC `NOT_FOUND`）
**同样属于"已配置"**——说明那个下载器确实存在、能连上，只是目标目录不存在。
若把它当成"没配"，就会得出"上游一个下载器都没有"的错误结论。

**这类报错会被翻译成人话再显示**。上游把整段 gRPC 异常（`StatusCode`、`details`、
`debug_error_string`、`created_time` 外加一串 RPC 内部字段）原样回给我们，
直接贴到页面上只会让用户以为配置坏了，事实恰恰相反。页面上现在看到的是：

> 下载器可用；它记录的目录 `/BON_115网盘/私存入库/AVdb` 在网盘上不存在，
> 因此列不出目录（不影响提交下载）。

因此本站的做法是：

- 点一次「检测」，对 `clouddrive / 115 / qbittorrent / transmission / thunder`
  各探一次，把**命中 configured 的第一个**自动选中；
- 界面用一张清单列出每个候选的结论（可用 / 上游未配置 / 上游不支持此类型），
  而不是一段大段文字；
- 若一个都没命中，则明确说"上游没有任何已配置的下载器"，而不是给一个空值；
- 结果**不会替用户保存**：只有点「保存设置」才会固化。

> 实测经验：上游若把 CD2（CloudDrive2）桥到 115 网盘，正确的标识是 **`clouddrive`**，
> 不是 `115`——填 `115` 只会得到 `未找到该下载工具配置`。

### 关于"为什么不做登录读配置"

上游把「有哪些下载器、各自能写哪些目录」放在自己的配置里，读取接口是
`GET /api/v1/config/{key}`，它**只接受登录 JWT**（用户名 + 密码换来的），
访问令牌无权调用。

但**这并不意味着必须让用户填账号密码**——真正需要的"上游默认下载目标"
在 `default-rule` 里就有，而那个接口接受访问令牌。所以本项目：

- 完全不碰 `/api/v1/users/login`，设置页没有用户名/密码输入框；
- 配置里不含密码、不含 JWT（有测试直接扫磁盘配置文件兜底）；
- 不缓存上游配置原文——那里面可能有网盘 Cookie。

这也是与旧脚本最大的区别：`_老脚本main.go` 要求你手工编辑 `config.json` 里的
`default_downloader` / `default_save_path`，填错同样只会在提交下载时看到一句
「未找到下载器」，而且它没有任何手段帮你查出正确值。

### 密钥为什么是掩码

API Key 与访问口令在页面上**只显示掩码**（如 `fpOJ••••••••1BZ`），输入框永远不回显明文。
需要修改时直接粘贴新值；留空表示不修改；勾选「清除」才会清空。

这样做是刻意的：上游官方文档明确要求访问令牌不得进入前端，
而页面 HTML 会经过浏览器缓存、代理日志和截图。掩码既能让你确认"已配置"，
又不会在链路上留下完整凭证。

### 配置优先级

```
内置默认值  <  环境变量  <  配置文件（页面保存的值）
```

配置文件排在最后，因为那是你自己在页面上显式改过的内容——
如果反过来，就会出现"改完刷新又变回去了"这种最难排查的问题。
环境变量在这里的角色是**首次启动的初值**（容器部署时用来预置），不是最终裁决者。

> **例外**：监听地址（`AVDB_ADDR`）与配置目录（`AVDB_CONFIG_DIR`）属于部署参数，
> 永远由环境变量决定，不受配置文件影响——改它们需要重启，让它们在页面上"看起来能改"
> 只会制造误解。

想用环境变量重新接管某个字段，删掉 `data/config.json` 里对应的键即可。

## 浏览器右键搜索

服务端同时接受这些写法，随便用哪种：

| 模板 | 用在哪儿 |
| --- | --- |
| `/s?q=%s` | Chrome / Edge / Firefox 的「自定义搜索引擎」 |
| `/s?q={searchTerms}` | OpenSearch 规范 |
| `/s?q={{ q }}` | 各类右键菜单插件的自定义模板 |
| `/s/{关键词}` | 路径式，部分书签工具更顺手 |

参数名除 `q` 外，还兼容 `keyword`、`kw`、`wd`、`query`、`s`。

### 方式一：一键添加（OpenSearch）

访问 `http://<你的地址>:8080/`，点首屏的「添加为搜索引擎」。
浏览器会自动识别并提示加入搜索引擎列表。

### 方式二：Chrome / Edge 手动添加

1. 打开 `chrome://settings/searchEngines`
2. 找到「网站搜索」→「添加」
3. 填入：
   - 名称：`资源搜索`
   - 快捷字词：`av`（可选，之后在地址栏敲 `av ` + 空格即可搜索）
   - 网址：`http://<你的地址>:8080/s?q=%s`
4. 保存

之后地址栏输入 `av 关键词` 直接搜；选中文字后右键「使用 资源搜索」也可（取决于浏览器/插件）。

### 方式三：右键菜单插件

各类支持自定义搜索引擎的右键插件，把请求地址填成：

```
http://<你的地址>:8080/s?q={{ q }}
```

插件自己的占位符写法照它的要求写，服务端三种都认。

### 关键词处理

- **中文、英文、日文假名、数字、混合写法**都支持，走标准 URL 编码
- **全角自动转半角**：中文输入法下很容易打出全角番号（`ＢＯＢＢ－４５６`），
  直接送上游一条都搜不到，服务端会先折成半角 `BOBB-456` 再查询
- 连续空格折叠、首尾空白裁掉、控制字符剔除
- 超长关键词截断到 200 字符

## 访问控制

默认**不启用**。设置「访问口令」后，所有页面都需要先通过校验：

```
http://<你的地址>:8080/s?q=关键词&token=你的口令
```

首次带 `token` 访问会写入 Cookie（30 天），之后不用重复携带。
也可以用请求头 `X-Auth-Token`。

`/healthz` 始终免鉴权，否则容器编排无法探活。

> **注意**：本站代理了「提交下载」这一会改变状态的操作，而且持有你的上游令牌。
> 如果打算把它暴露到公网，**务必**设置访问口令，并建议在反向代理上再加一层认证。
> 只在内网使用时，不设也可以。
>
> 「提交下载」另有两道与口令无关的收口：**只接受 POST**，并且校验请求来源（同源）。
> 两者缺一不可——只用来源校验挡不住把 `referrerpolicy` 设成 `no-referrer` 的
> `<img src=".../download?tid=1">`，而只改方法不给来源校验则挡不住跨站表单提交。

## 环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `AVDB_API_BASE_URL` | `http://127.0.0.1:8999` | 上游地址（初值） |
| `AVDB_API_KEY` | 空 | 上游令牌（初值） |
| `AVDB_DOWNLOADER` | 空 | 下载器标识（初值）；留空时提交下载用兜底值 `clouddrive` |
| `AVDB_SAVE_PATH` | 空 | 下载保存路径（初值）；**留空会导致提交下载被本站拦下** |
| `AVDB_PAGE_SIZE` | `100` | 每页条数；取 `10/50/100/200/300/500/1000`，**`0` 表示一次显示全部** |
| `AVDB_ACCESS_TOKEN` | 空 | 本站访问口令 |

| `AVDB_MAX_RESULTS` | `0` | **可选**安全阀：`0`（默认）= **不限制**；非负整数，上界 50000。**部署参数：只认环境变量，配置文件里的 `max_results` 已退役不再生效** |
| `AVDB_ADDR` | `:8080` | 监听地址（部署参数，仅环境变量生效） |
| `AVDB_CONFIG_DIR` | `.` | 配置目录（容器内已是 `/data`） |
| `AVDB_DISABLE_ORIGIN_CHECK` | 空 | 设为 `1` 关闭来源校验（仅用于反向代理无法回传原始主机时的应急，会削弱 CSRF 防护） |
| `PORT` | — | `AVDB_ADDR` 未设时的备选 |
| `TZ` | — | 时区，影响日志时间戳 |

> `AVDB_PAGE_SIZE=0` 是**合法值**（表示全部），不是"没设置"。
> 因此配置装载时该字段会被显式初始化为默认值，而不是靠"零值即默认"的逻辑兜底。

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 首页；带 `?q=` 时直接出结果 |
| GET | `/s?q=关键词` | **搜索主入口**，浏览器搜索模板用这个 |
| GET | `/s/{关键词}` | 路径式搜索 |
| GET | `/search?keyword=关键词` | 兼容旧地址 |
| GET | `/api/search?q=关键词` | JSON 结果 |
| POST | `/download` | 提交单条下载（表单字段 `tid` 或查询串 `?tid=`），返回 `{success, message}` |
| POST | `/download/batch` | **批量提交下载**（表单字段 `tids`，逗号/空格/分号分隔，单批 ≤100） |
| GET | `/settings` | 设置页面 |
| POST | `/settings` | 保存设置 |
| POST | `/api/settings/test` | 测试上游连通性 |
| POST | `/api/settings/downloaders` | **探测上游已配置的下载器**，返回 `{downloaders: [...], best}` |
| POST | `/api/settings/default-rule` | 读上游全局默认下载目标（`{downloader, save_path, save_path_label}`） |
| POST | `/api/settings/directories` | 用已有令牌校验下载器标识并列出其目录（表单：`downloader_id`） |
| GET | `/opensearch.xml` | OpenSearch 描述文档 |
| GET | `/healthz` | 健康检查（含 `version` 与 `build`） |
| GET | `/static/*`、`/favicon.svg` | 静态资源 |

搜索类接口通用分页参数：

| 参数 | 说明 |
| --- | --- |
| `page` | 页码，从 1 起；序号**跨页连续**（第 2 页从 101 起，而不是从 1 重新数） |
| `page_size` | 每页条数，取 `10/50/100/200/300/500/1000`；**`0` = 全部**。在结果页 URL 上带该参数会**立即落盘**，之后一直用它 |
| `site` / `section` / `category` | 精确匹配的筛选条件，空即不筛 |
| `flags` | 属性筛选，逗号分隔，多个之间是**与**（`cn` / `unc` / `uhd` / `hd`） |
| `sort` | `default` / `size-desc` / `size-asc` / `time-desc` / `time-asc` |
| `filter` | 标题关键词过滤，空格或逗号分词，`-词` 表示排除 |

筛选与排序对 `/s`（HTML）和 `/api/search`（JSON）**完全一致**——同一份实现，
不会出现"页面上筛出来的条数和接口返回的对不上"。

页面上的「每页」下拉与设置页的「每页条数」写的是同一个配置项，两处都能改，改完都是永久的。

接口在施加了筛选时，`total` 是**筛选后**的条数，并用 `total_all` 给出筛选前的总数
（未筛选时两者相等），`applied_filters` 回显当前生效的条件：

```json
{
  "total": 125, "total_all": 250, "filtered": true,
  "applied_filters": { "site": "色花堂", "flags": ["cn"], "filter": "-4K" }
}
```

`count` 始终是**本页**条数，`total` 才是命中总数——这两个在加了分页之后最容易搞混，
所以刻意分开。

`/download/batch` 的行为：单批最多 100 条、固定 4 路并发、**单条失败不影响其余**，
返回逐条结果且**与提交顺序一一对应**；超过 100 条会要求分批，不会静默截断。

四个 `POST /api/settings/*` 都要求同源
（`Origin`/`Host` 口径与 `POST /settings` 一致），且都**只用访问令牌**：
不要求上游账号密码，也不写入配置——读到的值只是回给页面看一眼，
要不要固化成自己的配置由用户点「保存设置」决定。

它们都遵循同一条入参约定：**目标字段留空 = 沿用已保存的值**。
`api_base_url` 与 `api_key` 都是如此，两者的口径刻意保持一致
（曾经一个"留空即空地址"、一个"留空即沿用"，页面上看不出来，
直连接口的调用方却会收到「上游 API 地址为空」这种与事实不符的报错）。

`/api/settings/default-rule` 在"上游只配了目录、没配下载器"时会返回
`success: false` 并把目录照样带回——因为不填下载器解决不了用户的问题，
但那个目录是真实可用的，不该跟着一起丢掉。

### `GET /api/search` 响应示例

```json
{
  "keyword": "BOBB-456",
  "count": 2,
  "total": 3133,
  "page": 1,
  "total_pages": 16,
  "page_size": 200,
  "torrents": [
    {
      "id": 10080460000,
      "title": "BOBB-456 [BT](ABC) ...",
      "site": "x1080x",
      "section": "亚洲有码",
      "category": "",
      "size_mb": 5244,
      "post_time": "2026-02-22 20:13:14",
      "download_url": "magnet:?xt=urn:btih:...",
      "preview_image": "https://.../off_BOBB-456.jpg",
      "chinese": false,
      "uncensored": false,
      "hd": true,
      "uhd": false
    }
  ],
  "sites": ["x1080x"],
  "sections": ["亚洲有码"],
  "categories": [],
  "truncated": false
}
```

- `count` 是**当前页**条数，`total` 才是总命中数；
- `page_size` 为 `0` 表示不分页（一次返回全部）；
- `truncated` 为 `true` 表示命中数超过了**显式配置**的安全阀（默认 `0` = 不限制）——
  正常配置下它永远是 `false`，搜索无结果上限。

失败时返回 `{"error": "..."}`，HTTP 状态码 `502`。

**排序稳定性与未知时间沉底**、**`apply()` 不污染搜索缓存**、
**筛选栏"一行到底"的样式契约（`flex-wrap: nowrap` + 下拉定宽 + 980px 兜底）**、
**网站名称开关（默认关闭 / 开启生效 / 空关键词不产生孤立分隔符 /
关键词转义 / 存档往返 / 默认值不落盘 / 不可由 URL 改）**。

真实链路的冒烟检查另有一层：`scripts/smoke.sh` 对运行中的实例打请求，
用法与判据见该脚本头部。它的两个断言助手（`contains` / `missing`）**刻意不用管道**——
脚本开了 `set -o pipefail`，而 `grep -q` 一命中就退出，管道写端会吃 SIGPIPE(141)，
于是"命中"被报成"未找到"。触发条件是响应体大于管道缓冲（约 64KB）且命中点靠前，
也就是**结果条数一多才会发作**，寥寥几条时一切正常，属于很难自己暴露的哑雷。
现在统一用 here-string（bash 以临时文件实现）喂 grep，两个方向都不会误判。

## 常见问题

**搜索结果 401**

上游令牌不对或没填。去 `/settings` 点「测试连接」会直接告诉你原因。

**页面能开，但点「下载」失败**

先看提示原文，现在会照实转述上游的校验结果并补上"下一步该做什么"，照做即可：

- `保存路径未配置：请到设置页填写「保存路径」后再提交`
  上游要求 `save_path` 必填且不能为空，本站直接挡住了这次提交（**没有打到上游**）。
  去 `/settings` 填一个目录即可。
- `上游参数校验失败（422）：查询参数 → downloader：Field required`
  说明上游把 `downloader` 也改成了必填。本站现在**无条件发送**该参数，
  正常不会再出现这条；若仍出现，说明上游字段名或接口路径又有变动，
  把提示发出来即可定位。
- `上游没有找到下载器 "xxx"`
  你在设置页选的标识上游不认。点「检测」拿回真实标识再保存。

**想知道自己跑的镜像是哪次构建**

看页面**右上角**的版本徽标：显示的是**版本号**（如 `v1.1.0`），
打 tag 发布时就是 tag 本身。想看具体构建，去设置页「运行信息」里的
「构建」一项（形如 `main@10acaaa`），`/healthz` 也会返回同样的值。
命令行用 `avdbasst -version` 能同时拿到版本号与构建标识。

**容器重启后配置回到默认值**

卷没挂上。确认 `docker compose` 里写了 `- ./data:/data`，
并且 `/settings` 页面上「配置目录」显示为可写。

**页面上保存配置提示失败**

配置目录不可写。用 `docker compose logs avdbasst` 看具体错误；
常见原因是宿主机目录属主不对。镜像入口脚本会在以 root 启动时
自动对齐 `/data` 属主，若仍然失败请检查挂载是否为只读。

**保存设置返回 403「跨站请求被拒绝」**

服务端会校验请求来源，防止别的网站借你的浏览器改配置。若本站部署在反向代理后面，
而代理没有把原始主机名回传给后端，就会出现「页面打得开、一保存就 403」——
后端看到的 `Host` 是内部地址，浏览器的 `Origin` 却是外部域名，两边对不上。

让代理回传原始主机即可，Nginx 示例：

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Real-IP $remote_addr;
}
```

403 页面会直接列出实际收到的 `Origin` / `Referer` / `Host` / `X-Forwarded-Host`，
照着对比即可定位。若确认同源却仍被拦截，可临时设 `AVDB_DISABLE_ORIGIN_CHECK=1`
关闭该校验——注意这会同时关掉这一层 CSRF 纵深防御，不建议长期开启。

**想看到海报图**

结果页按设计**只显示文字列表**，不再加载海报：这类图片多为站点防盗链资源，
加载慢、失败率高，而列表场景真正用来判断的是番号、体积与标签。
（「做种数」与「免费」标签已按需求从界面移除；上游返回的 `preview_image`
仍会出现在 `/api/search` 的 JSON 里，已做协议白名单，需要图片的自建前端可直接取用。）

**日期和上游差一天**

不会。展示的日期直接取自上游返回的 `post_time`，不做任何时区换算。
鼠标悬停在日期上可以看到上游原始时间串。

**搜索很慢**

默认超时 20 秒。上游是本地服务的话可以在设置里调小到 5–10 秒，
失败能更快暴露。客户端偶发连接抖动会自动重试一次。

### 几个实现上的选择

- **前端零内联脚本**，全部走外部文件 + 事件委托，因此 CSP 可以收紧到
  `script-src 'self'`。上游标题属于外部不可信输入，一旦用 `innerHTML` 拼接
  就是存储型 XSS，所以所有数据都经模板转义后放进 `data-*` 属性。
- **搜索结果服务端直出**，浏览器禁用 JS、或插件只做"打开 URL"这一动作时，
  页面依然是完整的。
- **筛选下拉的顺序是显式排序的**。用 map 遍历生成会让同一份数据每次刷新顺序都不同，
  属于"同一输入两次结果不一致"的安静型故障，测试里连跑 200 次做回归。
- **协议白名单**。上游返回的 `download_url` / `preview_image` 只放行
  `magnet/http/https/ed2k/thunder/ftp`，避免上游数据被污染后把 `javascript:` 带进页面。
- **凭据的单向闸门**。本站不接收任何上游账号密码，所以请求侧没有密码可漏；
  需要设防的是响应侧——上游配置里可能躺着网盘 Cookie、账号令牌，因此只按白名单
  键名摘取 `path`/`name` 这类字段，绝不把上游配置整段回传浏览器。
  有一条测试专门盯着这件事：塞一段带 `SECRET-COOKIE-VALUE` 的假配置进去，
  断言它不会出现在结果里。
- **不把"没读懂"伪装成"上游没有"**。读 `default-rule` 时，如果响应里连一个
  认识的字段都没有，会报错并附上原文，而不是安静地返回空规则——后者会让界面显示
  "上游没有配置默认下载目标"，把人引去上游翻配置，而真实原因是接口结构变了。
- **分页在服务端完成，序号跨页连续**。上游一次返回全量（实测关键词 `SSIS` 有 3133 条），
  分页只是对结果切片，因此筛选下拉的候选值始终基于**全量**计算，
  不会出现"翻到第 2 页后筛选项变少"这种随页码漂移的怪现象。
- **筛选、排序、过滤同样在服务端**，并且先于分页发生。顺序反了的话，
  排序只会作用在当前页这 100 条上，翻页就是另一套顺序；
  筛选条件则通过 `pagerURL` / 跳页表单的 hidden 字段全程传递，
  这也是"筛完一翻页条件就没了"的根治办法。
- **筛选项的长度有上限**（64 字符）。超长值视作"没选"而不是截断后拿去比较——
  截断后的值永远匹配不上任何条目，页面会变成一个空列表配一个看不出问题的下拉框。
  同理，筛选项的值**不做 TrimSpace**：它要拿去和 `t.Site` 做等值比较，
  归一化会让下拉里显示的"abc"永远匹配不上实际存着" abc"的那条。
- **`apply()` 返回的切片永远是私有的**（没筛选时也拷贝一份）。
  紧接着要对它按排序模式**就地重排**，而入参很可能是搜索缓存持有的那一份——
  共享的话会把缓存里的顺序改掉，用户切回「默认」排序时再也拿不到上游原本的次序。
- **结果页带 `page_size` 视为显式设置**。它会被立即写入配置文件——
  用户要的是"设一次就一直用它"，而不是"这次请求用一下"。
  相应地，配置里 `PageSize=0`（全部）是**合法值**，不能按"零值即未设置"处理，
  否则用户选「全部」会被悄悄改回默认的 100（这个坑在测试里被当场抓到过）。
- **翻页有 2 分钟短缓存**。按 `上游地址 + 关键词` 作 key 缓存 8 条结果，
  翻页时不必把同一份数据再向上游要一遍；key 里带上游地址，
  是为了让"改了上游地址"立刻失效，不至于把上一个上游的结果喂给新上游。
- **`老脚本main.go` 保留但从构建中排除**。它是最初手工跑通的版本，作为"上游接口该怎么调"
  的参考件留着；文件名前的下划线让 Go 工具链忽略它（它和主包重名 `main`），
  `.gitignore` 也已排除 `_老脚本*.go`。注意它**不支持**自动读上游配置：
  `default_downloader` / `default_save_path` 全靠手工编辑 `config.json`。

### 下载器踩坑记录

这三个参数被同一条接口教训了四次，每次"修好"都在为下一次挖坑。
记在这里是因为它们的错法**一个比一个更像是对的**：

| 轮次 | 发出去的请求 | 上游回应 | 错在哪 |
| --- | --- | --- | --- |
| 1 | `downloader=115`（漏了 `save_path`） | 422，只报 `save_path` missing | 以为两个参数一起"必填"，其实当时只有 `save_path` 是 |
| 2 | `downloader=`（空串） | `未找到下载器` | 把"未设置"编码成了空串，上游去查一个 id 为空的下载器 |
| 3 | `downloader=115`（猜的固定值） | `未找到下载器: Downloader.115` | 猜了一个上游根本没有的标识（真实标识是 `clouddrive`） |
| 4 | 省略 `downloader`（"留空即省略"） | 422，`downloader：Field required` | **上游把契约改成了必填**，省略反而成了错 |

第 1 轮之后"两个参数都必须发送"是错的；第 2 轮之后"`downloader` 必须非空"也是错的；
第 3 轮之后"留空就该省略参数"同样是错的。真正的规则是
**三个参数各有各的语义，且两个都不能为空**，见前面那张表。

贯穿四轮的关键教训：**"上游文档标选填"不等于"上游现在仍然选填"**——
第 1、4 两轮的坑都来自把文档当作契约本身。文档只描述意图，实测才是契约。

另外两次误导来自文档措辞：`API接口2.md` 里"为空时继承全局订阅下载器"讲的是
`JavdbSubscriptionRuleForm`（订阅规则），与 `download/manul` 不是一个接口；
而 `download/manul` 的 `save_path` 与 `downloader` 都标注"选填"，实测缺失即 422。

现在的回归测试用 `q["downloader"]` 而不是 `q.Get("downloader")`
判断存在性——`Get` 对"没有该键"和"键存在但值为空"返回同样的空串，
而这两者在**上游眼里天差地别**，用错方法测试就守不住任何东西。
当前钉住契约的用例：`TestSubmitDownloadAlwaysSendsAllQueryParams`（三参数必发）、
`TestDownloadRequiresConfiguredSavePath`（空路径不打上游）、
`TestEndToEndDownloadAgainstStrictUpstream`（对着会返 422 的假上游跑通全链路）。
